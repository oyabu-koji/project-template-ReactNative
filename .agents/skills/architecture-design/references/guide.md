# アーキテクチャ設計ガイド

## 設計判断の書き方

各判断を次の順で記述する。

1. 対応する要件・品質特性
2. 採用する方式
3. 採用理由
4. 代替案と不採用理由
5. 制約・トレードオフ
6. 検証方法

「一般的だから」「最新だから」だけを理由にしない。

## 境界の例

- UI: 画面描画、入力、アクセシビリティ。
- Application: ユースケース、状態遷移、非同期処理の調停。
- Domain: ReactやExpoへ依存しない規則と計算。
- Platform: Expo API、端末機能、永続化、外部I/O。

プロジェクトに適合しないレイヤーを機械的に追加せず、採用した各境界について責務、公開インターフェース、依存方向、禁止事項を定義する。

## 品質特性

- 性能: 測定対象、目標、端末・データ条件。
- 信頼性: 失敗の隔離、再試行、フォールバック。
- セキュリティ: 入力、秘密情報、権限、ログ。
- プライバシー: 収集データ、保存場所、保持期間。
- アクセシビリティ: 操作、読み上げ、視認性。
- オフライン: 要件がある場合の機能範囲と同期方針。

## Expo・React Native

- Expo managed workflowで実現可能か確認する。
- 端末APIをUIへ直接結合せず、利用不可・拒否・失敗時の振る舞いを示す。
- Expo関連依存は`npx expo install`とSDK互換性を前提にする。
- NodeとExpo SDKは明示依頼なしに更新しない。

## テスト対応

- Domain境界はunit test候補を示す。
- UIとApplication境界はcomponentまたはintegration test候補を示す。
- 端末機能はシミュレータ・実機確認の対象を示す。
- 存在する品質scriptだけを実行し、未定義scriptを要件化しない。

## 完成チェック

- 技術判断がPRD・機能設計へ追跡できる。
- 責務と依存方向が明確で循環していない。
- 失敗時と端末差異の扱いがある。
- MVPに不要な仕組みを先回りして導入していない。
